# Правила проекта Rozetka 2.0

## Проект и работа

- Rozetka 2.0 — маркетплейс для покупки и продажи товаров разных продавцов.
- Интерфейс проекта — только на английском: тексты, сообщения ошибок и метаданные. Для шрифтов подключай только латиницу.
- `plan.txt` — главный источник задач, их статусов и стека. Перед работой читай его.
- Только пользователь редактирует `plan.txt` и отмечает выполнение задач. Не изменяй и не форматируй этот файл.
- Отвечай на русском, кратко и без повторов. Перед изменениями опиши план, после — результат.
- Сначала изучи связанный код; переиспользуй существующие компоненты и решения.
- Выбирай простой читаемый код без лишних абстракций, файлов и зависимостей.
- Не усложняй решение и не добавляй функциональность на будущее.
- Если задача непонятна, уточни у пользователя.
- Меняй только относящееся к задаче. Не переписывай, не переименовывай и не форматируй посторонний код.
- О неопределённости и препятствиях сообщай прямо.

## Дизайн

- `design/home-page.jpg` — референс общего визуального стиля для всех страниц. Перед работой изучи его; состав блоков определяет задача.
- Сохраняй контраст тёмного каркаса и светлого контента, зелёные акценты, простую типографику, умеренные скругления и контурные иконки.
- Переноси из референса палитру, пропорции, отступы и визуальную иерархию, адаптируя их под назначение экрана и размер устройства.
- Цвета задавай через переменные CSS или тему Tailwind; шрифты настраивай централизованно.
- Обеспечивай читаемый контраст, управление с клавиатуры, подписи полей и удобные области нажатия. Предусматривай состояния загрузки, отсутствия данных и ошибок.

## Структура и компоненты

- Сохраняй текущую структуру Next.js с `app/`; не добавляй другой роутер и не переноси код в `src/` без задачи.
- Создавай папки только по необходимости: `api`, `assets`, `config`, `constants`, `components`, `hooks`, `utils`, `lib`, `services`, `schemas`, `stores`, `types`, `providers`.
- В `components/ui` размещай базовые элементы, в `components/layout` — каркас страниц, в `components/elements` — предметные компоненты.
- Используй алиасы `@/*` вместо длинных относительных импортов.
- Ограничение для файлов кода — 100 строк. Разделяй их по ответственности, без искусственных абстракций.
- Один компонент — один файл;
- Используй функциональные компоненты и деструктуризацию props в аргументах.
- Для условного рендеринга в компонентах используй тернарный оператор вместо `if` с отдельными `return`. Взаимоисключающие состояния объединяй в один блок условий; простые вложенные тернарные операторы допустимы, если читаются понятно. Для отображения без альтернативной ветки используй `&&` вместо `? ... : null`. Сложные ветки выноси в отдельные компоненты.
- Страницы оставляй небольшими; сложную бизнес-логику выноси в сервисы или хуки.
- Крупные условные блоки и элементы списков выноси в компоненты, сложные вычисления — из JSX.
- Используй именованные экспорты; `default` — когда этого требует фреймворк или библиотека.

## Состояние и API

- Локальное состояние — `useState` или `useReducer`, рядом с местом использования.
- TanStack Query используй для запросов, кеширования, мутаций и инвалидации; Jotai — только для общего клиентского состояния.
- Ключи TanStack Query бери из `config/query-keys.config.ts`, включая ключи для инвалидации и очистки кеша.
- Не отключай повторные попытки запросов через `retry: false`; используй настройки TanStack Query по умолчанию.
- Папки загрузки и URL медиа с бэкенда получай через `config/media.config.ts`; не дублируй пути в компонентах.
- Не копируй серверные данные в Jotai или локальное состояние; вычисляемые значения не сохраняй отдельно.
- Запросы и бизнес-операции размещай в `services`; не вызывай Axios или `fetch` непосредственно в UI-компонентах.
- Общий экземпляр Axios, базовый URL, заголовки, credentials и обработку ошибок храни в `api/axios.api.ts`.
- Не создавай лишних запросов, запросов в циклах или дополнительных экземпляров Axios без причины.
- Учитывай сессионную авторизацию бэкенда; не придумывай API, формат ответов и способ хранения сессии без контракта.
- Схемы Zod храни в `schemas`; не дублируй правила валидации.
- Обрабатывай отклонённые промисы и ошибки запросов; не подавляй их молча и не показывай пользователю внутренние ошибки сервера.
- Не дублируй централизованную обработку ошибок и не добавляй лишние `try/catch`.

## TypeScript и именование

- Не используй `any`. Предпочитай вывод типов, когда явная аннотация ничего не добавляет.
- Для уже описанных сущностей переиспользуй существующие типы через `Pick`, `Omit`, `Partial` или обращение к типу поля; не дублируй их поля inline, в том числе в параметрах маршрута.
- Интерфейсы начинай с `I`, типы — с `T`, enum - c `E`; используй `import type`.
- Props компонентов описывай отдельным интерфейсом или типом, а не inline в аргументах функции.
- Компоненты и их файлы — PascalCase; остальные файлы — kebab-case с суффиксами по назначению: `users.service.ts`, `axios.api.ts`.
- Соблюдай обязательные имена файлов Next.js и существующие соглашения проекта.
- Переменные и функции — camelCase, константы которые содержат статическую информацию — ALL_CAPS.
- Используй понятные полные имена, короткие функции, удаляй мёртвый код и необоснованные TODO.
- Обработчики называй по действию: `onSubmitOrder`, `onChangeSearch`, `onOpenModal`.
- Булевы значения начинай с `is`.
- Разделяй разные логические действия одной пустой строкой, но не ставь пустую строку между каждой строкой кода.

## Стили и производительность

- Используй Tailwind через `className`, условные классы объединяй через `cn`.
- Стандартные иконки импортируй отдельно из lucide-react; собственную графику можно хранить в SVG.
- Подбирай размеры изображений, сохраняй пропорции и предотвращай скачки разметки явными размерами.
- В компонентах `Image` явно указывай `width` и `height`; отображаемый размер и обрезку задавай через `className`.
- Используй оптимизацию изображений Next.js и отложенную загрузку вне первого экрана, где уместно.
- Простые переходы делай через CSS; предпочитай `transform` и `opacity`, 150–300 мс, учитывай `prefers-reduced-motion`.
- Используй `memo`, `useMemo`, `useCallback` и динамический импорт только при обоснованной необходимости.

## Проверки и форматирование

- Пользователь проверяет изменения самостоятельно. Не запускай тесты, линтер, сборку и автоматические проверки интерфейса.
- После изменений обязательно запускай `prettier --write` для всех созданных и изменённых файлов, поддерживаемых Prettier, с настройками проекта из `.prettierrc`. Не форматируй посторонние файлы и `plan.txt`.
